# 方案总览

| 方案       | 组成           | 查询方式                     |
| -------- | ------------ | ------------------------ |
| **方案 A** | 纯 B+ 树       | 点查/范围查都走树，逐层追指针（树高 ~3 层） |
| **方案 B** | B+ 树 + 自适应哈希 | 点查先查哈希；命中直接返回，未命中回退到树    |
**"自适应"** 的意思是：哈希**不是一开始就建**，而是某个 key 被访问达到 `HASH_THRESHOLD`（这里=2）次后，才把它**拉进哈希表**当缓存。这样只有热点 key 进哈希，避免给全量数据建哈希的开销。

# 预期结论：

- **点查**：B 明显快（热点 key 走哈希，O(1) vs 树高 O(log n) 层指针）
- **插入/删除**：B 略慢或持平（要维护哈希，但只在访问时才建）
- **范围查**：两者一样（都走同一棵 B+ 树，哈希不参与）
- **结果必须完全一致**（checksum 相同）

# 具体设计
## `main` 流程
```
`main` 流程
1. selfTest()                     // 先保证正确
2. makeData / makePointQueries / makeRangeQueries
3. 打印实验参数
4. runBench(A) + runBench(B)      // 各跑 3 轮，取最好
5. 打印对比表（插入/点查/范围查/删除/命中率/校验和/剩余条数）
6. insertOnly 对比写入代价
7. 打印结论：点查提速约 X 倍；范围查差异在噪声内
```

## 参数定义

```C++
KEY_COUNT         = 10000   // 插 1 万条
HOT_KEY_COUNT     = 1000    // 其中 1000 个是热点
POINT_QUERY_COUNT = 10000   // 跑 1 万次点查
RANGE_QUERY_COUNT = 100     // 跑 100 次范围查
WARMUP_COUNT      = 100     // 预热 100 次（两方案相同，公平）
RUNS              = 3       // 每类测量跑 3 轮取最好
TREE_ORDER        = 8       // B+ 树阶数
HASH_THRESHOLD    = 2       // 访问 2 次后进哈希
HASH_BUCKETS      = 4096    // 哈希桶数
HOT_PERCENT       = 80      // 80% 的查询打热点 key（模拟真实倾斜）
```
**`HOT_PERCENT=80`**——80% 点查落在 1000 个热点 key 上（符合真实的"二八分布"）。这决定了哈希能带来多大收益：热点越集中，自适应哈希越划算。

## 对比实验

```
template <typename PlanType>
static BenchResult runPlan(PlanType& plan, ...) {
    // 1. 插入 1 万条，计时 → insert_ms
    // 2. 预热：前 100 条点查（两方案相同）
    // 3. 点查 1 万次，计时 → point_ms（累加 value 防优化掉）
    // 4. 范围查 100 次，计时 → range_ms（同样累加）
    // 5. 删除 1 万条，计时 → delete_ms
    // 6. 返回 checksum（累加和，用于验证 A/B 结果一致）
}
```
**用模板让 A、B 跑完全相同的流程**，只有 `plan.xxx()` 内部实现不同——这是公平对比的关键。

## benchmark 方法论

比一般"随手跑个耗时"专业的地方：

| 做法             | 目的              |
| -------------- | --------------- |
| 固定随机种子         | 结果可复现           |
| 先 selfTest 再跑分 | 保证"快"不是"算错"     |
| 暴力数组对拍 6000 步  | 抓数据结构边界 bug     |
| A/B 跑同一模板流程    | 排除流程差异，只比"查表方式" |
| 预热             | 进入稳态            |
| checksum 累加    | 防优化掉 + 验证结果一致   |
| 一次只活一棵树        | 避免 cache 争用，公平  |
| best-of-3      | 抗测量噪声           |
| insertOnly 单测  | 验证写入无额外代价       |

## index_compare.h流程

这是**适配器（Adapter）封装层**，把底层的 `BPlusTree` 和 `HashIndex` 组合成两个**对外接口完全一致**的类 `IndexPlanA` / `IndexPlanB`，让 `runPlan` 模板能用同一份代码测两种方案。同时它实现了"**自适应哈希**"的核心策略。

底层有两个独立组件
- `BPlusTree`（`bplus_tree.h`）
- `HashIndex`（`hash_index.h`）

模板语法`template<class PLANTYPE>`在[[DB_C++_语法]]

但 `runPlan` 是模板，要求 A、B 有**完全相同的方法集**：`insert / erase / search / rangeScan / size / treeHeight / hashEntries / hitRate`。

```
        runPlan<PlanType>
               │
     ┌─────────┴─────────┐
IndexPlanA            IndexPlanB
  │                     │
BPlusTree          BPlusTree + HashIndex×2
```

A 和 B 对外签名一致 → 同一个模板跑两边 → 对比公平。

### 两种方案概述

| 方案 A     | 方案 B        |                                             |
| -------- | ----------- | ------------------------------------------- |
| **名称**   | 纯 B+ 树      | B+ 树 + 自适应哈希                                |
| **结构**   | 仅一棵 B+ 树    | B+ 树（唯一数据源）+ 两个哈希表(一个是热点键值对，一个是键和访问次数，两表写作) |
| **点查路径** | 逐层追指针，O(树高) | 先查哈希，命中 O(1)；未命中回退 B+ 树                     |
| **范围查**  | 走 B+ 树      | 走同一棵 B+ 树，哈希不参与                             |
| **定位**   | 基线/对照组      | 优化方案                                        |

## 二、对照分析

**1. 主对比：点查提速 1.36x，写/范围查零代价，删除 +23.4%**

- 插入 +0.7%、范围查 +0.1%，**符号近零、属噪声**——B 插入只写 B+ 树、范围查只走树，符合设计。
    
- 删除 +23.4% 是**增加了复杂度带来的代价**：三处同步删除导致（cache、counts、树）。
    

**2. 热点扫描：提速随命中率单调变化**

- 命中率 11%→0.63x、44%→0.97x、71%→1.70x、0%→0.59x。**命中率是直接决定因素。**
    

**3. 同样是 80% 热点，热点 key 数独立影响提速**

- 80%/**5000**：1.70x（命中率 71.3%，条目 6819）
    
- 80%/**10000**：1.37x（命中率 62.4%，条目 11704）
    
- **同样的热点占比，热点 key 越少越快。** 原因：key 越少 → 每个被查次数越多（平均约 16 次 vs 8 次）→ 晋升的固定成本（前 2 次未命中）平均下来减小 → 命中率更高、缓存更小、负载因子更低。
    

**4. 回本点 ≈ 命中率 45%**

- 50% 档命中率 44.3% → 0.97x，刚好在回本点附近；低于此 B 净亏（如 0% 档 0.59~0.63x），高于此 B 净赚（如 80% 档 1.37~1.70x）。**仅对此参数设计而言**。

---

## 三、结论

1. **点查提速 1.35x（主配置），插入与范围查零代价，结果完全一致，删除 +22% 为固有开销。**
2. **提速由命中率决定，回本点约 45%**：命中率不过半即净亏（0% 档 0.55~0.62x），过半才回本（80% 档 1.35~1.74x）。
3. **热点 key 数本身是独立影响因素**：同样 80% 查询打热点，5000 个 key（1.74x）明显优于 10000 个（1.35x）——**热点越集中，收益越大、缓存反而越小**。
4. **适用边界**：读多写少、热点集中场景收益最大；均匀访问反而略亏；删除有约 22% 代价
5. **需要根据实际情况，调整参数！**
